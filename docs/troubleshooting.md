# ACT 复刻中的问题定位记录

## Python 版本不满足要求

**现象** → Python 3.10 环境中安装被版本约束拒绝。  
**第一判断** → 我最初更关注缺哪个包，认为继续补依赖就能安装。  
**日志证据** → 安装器明确给出 LeRobot 需要 Python 3.12。  
**排查步骤** → `python --version`、`which python`、`python -m pip --version`，确认 pip 与解释器属于同一 Conda 环境。  
**真正原因** → 解释器版本属于硬约束，不是普通依赖缺失。  
**修复方法** → 新建 Python 3.12 Conda 环境后重新安装。  
**验证方式** → 三条版本命令都指向新环境，LeRobot 安装继续向下执行。  
**迁移经验** → 先检查 Python/CUDA/系统等平台约束，再处理包级依赖。

## NVIDIA/cuDNN 大依赖下载失败

**现象** → 下载 `nvidia_cudnn_cu13` 等大包时出现 timeout、SSL EOF 或不完整下载。  
**第一判断** → 我一度怀疑包版本本身不可用。  
**日志证据** → 错误发生在传输过程中，且重试时下载进度不同，没有稳定复现为解析冲突。  
**排查步骤** → 检查磁盘空间、网络稳定性、pip 缓存，并区分“下载失败”和“依赖求解失败”。  
**真正原因** → 根据当前日志，更符合大文件网络传输中断；不能据此断言版本不兼容。  
**修复方法** → 在网络稳定时重试，必要时增加 pip 超时或使用可信镜像；避免并行重复下载。  
**验证方式** → 包完整下载并通过安装校验，后续导入正常。  
**迁移经验** → SSL EOF 不等于 CUDA ABI 冲突，先看失败发生在哪个阶段。

## `typeguard` 依赖提示

**现象** → resolver 提示 `generate-parameter-library-py` 需要 `typeguard`。  
**第一判断** → 我最初把 resolver 的所有提示都当成安装已彻底失败。  
**日志证据** → 提示指出具体依赖关系，需要再用 import 或 `pip check` 判断环境是否真的不可用。  
**排查步骤** → `python -m pip check`，确认缺失包和要求版本。  
**修复方法** → 在同一环境中补装与当前依赖约束兼容的 `typeguard`。  
**验证方式** → `pip check` 不再报告该缺失项，相关模块可以导入。  
**迁移经验** → resolver warning、import error 和运行时异常是不同层级，不能混写成一个原因。

## 命令入口变化

**现象** → `python -m lerobot.record` 报 `No module named lerobot.record`。  
**第一判断** → 我先怀疑 LeRobot 没有正确安装。  
**日志证据** → 包可以导入，但指定模块路径不存在；安装后提供了 `lerobot-record` entry point。  
**排查步骤** → `python -m pip show lerobot`、`which lerobot-record`、`lerobot-record --help`。  
**真正原因** → 本地版本的 CLI 入口与旧教程不同。  
**修复方法** → 改用 `lerobot-record`。  
**验证方式** → `--help` 能显示本地版本支持的参数。  
**迁移经验** → 先相信本地 `--help`，不要把不同版本教程的模块路径强行拼在一起。

## 相机字典解析失败

**现象** → 相机参数无法被配置解析器读取，出现 YAML/字典解析错误。  
**第一判断** → 我先检查相机索引和设备是否在线。  
**日志证据** → 错误发生在程序连接相机之前，定位到参数字符串本身；其中一个字段之间缺少逗号。  
**真正原因** → 字典语法错误，而不是摄像头硬件故障。  
**修复方法** → 使用英文引号、成对大括号和字段间逗号；先单独打印或解析字典。  
**验证方式** → 配置通过解析，日志开始进入相机连接阶段。  
**迁移经验** → 用“错误发生在初始化的哪一步”区分配置层和设备层。

## 提前退出与空 episode

**现象** → 第三轮录制进入 Reset 后按键退出，相机与机器人随后断开，`save_episode` 失败。  
**第一判断** → 我起初把相机断开当成根因。  
**日志证据** → 时间顺序是按键触发 Stop 在前，设备断开在后，保存失败最后出现。  
**真正原因** → 提前退出使当前 episode 没有有效帧；相机断开是清理流程的一部分，不是最早异常。  
**修复方法** → 避免在 episode/reset 边界误触退出；保存前检查帧数，对空 episode 做丢弃而非编码。  
**验证方式** → 重新录制的 episode 元数据、帧数和视频文件一致。  
**迁移经验** → 按时间线找第一个异常事件，不要把最后一条 traceback 自动当根因。

## Hugging Face 401

**现象** → 数据上传或访问 Hub 时返回 401。  
**第一判断** → 容易误判为数据保存失败或 repo_id 拼写错误。  
**日志证据** → HTTP 状态明确指向认证/权限层。  
**排查步骤** → 独立检查登录状态、仓库所有者和数据集可见性；Token 不写入命令或仓库。  
**真正原因** → 当前会话未认证或没有目标仓库权限。  
**修复方法** → 在本机完成 Hugging Face CLI 登录，或选择纯本地保存。  
**验证方式** → 使用最小只读请求确认身份，再重试上传。  
**迁移经验** → 把本地落盘和远端上传拆成两个验证点。

## ACT 训练 CUDA OOM

**现象** → 训练尝试额外申请约 830 MiB 时失败；日志显示 15.47 GiB 总显存只剩约 710 MiB，当前进程已占用约 13.47 GiB。  
**第一判断** → 我最初觉得 16GB 显卡应该足够，怀疑是程序错误。  
**日志证据** → OOM 给出的已分配、保留和空闲显存说明工作负载已经接近上限。  
**排查步骤** → 查看 `nvidia-smi`、其他进程、batch size、双相机分辨率，并区分容量不足和碎片。  
**真正原因** → 当前配置的峰值显存超过可用空间；碎片可能加剧问题，但不能代替降低工作负载。  
**修复方法** → 降低 batch size，并设置 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 缓解碎片。  
**验证方式** → 训练跨过原 OOM 位置并持续更新 step；同时记录峰值显存。  
**迁移经验** → allocator 配置不是“增加显存”，首先仍要控制 batch、图像和模型负载。

## 部署观测不匹配

**现象** → checkpoint 能找到，但部署端可能在观测键或图像形状处失败，或表现明显异常。  
**第一判断** → 容易先怀疑权重损坏。  
**日志证据** → 训练数据使用 `handeye` 与 `fixed` 两路相机；部署配置若改名、缺一路或顺序/预处理不一致，模型输入语义已经变化。  
**修复方法** → 对照数据集特征和训练配置，保持相机名称、数量、分辨率与预处理一致。自动部署时移除 Leader teleop。  
**验证方式** → 在上扭矩前打印观测键与 shape，确认匹配后再做低风险动作测试。  
**迁移经验** → checkpoint 不只是权重文件，它隐含依赖训练时的完整观测定义。
