# 分类排错案例

[返回本分支 README](../README.md) · [返回 `main`](https://github.com/Zeil6/lerobot-so101-imitation-learning/tree/main)

## 一、环境与依赖类

### Python 3.10 与 LeRobot 要求不符

**现象** → 安装阶段提示需要 Python 3.12。  
**第一判断** → 继续补包可能解决。  
**日志证据** → 版本约束在依赖安装前已经拒绝当前解释器。  
**排查步骤** → 同时检查 `python --version`、`which python`、`python -m pip --version`。  
**真正原因** → Conda 环境解释器版本不满足项目要求。  
**修复方法** → `conda create -n lerobot python=3.12 -y`。  
**验证方式** → 三个命令都指向新环境，安装进入依赖阶段。  
**迁移经验** → 平台约束优先于包级排错。

### Editable install 与 Feetech extra

**现象** → LeRobot 源码可见，但 SO-101/Feetech 功能缺少依赖。  
**第一判断** → `pip install -e .` 已包含所有硬件依赖。  
**日志证据** → 项目把 Feetech 支持声明为可选 extra。  
**真正原因** → editable 只描述安装方式，extra 才描述额外依赖集合。  
**修复方法** → 在源码根目录使用 `python -m pip install -e ".[feetech]"`。  
**验证方式** → 相关模块可导入，SO-101 命令通过初始化。  
**迁移经验** → `-e` 与 `[extra]` 解决的是两个正交问题。

### FFmpeg 与视频编码

**现象** → 采集能显示画面，但 episode 视频保存/编码阶段异常。  
**第一判断** → 相机坏了。  
**日志证据** → OpenCV 已持续产出帧，错误出现在 H.264/x264 编码阶段。  
**排查步骤** → `ffmpeg -version`，检查编码器和输出目录权限/空间。  
**真正原因** → 需根据具体日志确认；不能仅凭编码日志断言相机故障。  
**修复方法** → 安装匹配环境的 FFmpeg，并用短样例验证编码。  
**验证方式** → 输出视频可被 `ffprobe` 读取，帧数与 episode 元数据合理。  
**迁移经验** → 采集、编码和上传是三段链路。

### pip timeout、SSL EOF 与 resolver warning

**现象** → cuDNN 大包下载中断；另有 `typeguard` 依赖提示。  
**第一判断** → 把所有红色输出归为同一个版本冲突。  
**日志证据** → timeout/EOF 发生在传输层，resolver 指向依赖关系，二者阶段不同。  
**排查步骤** → 检查磁盘/网络与 `pip check`，分别处理。  
**真正原因** → 前者初步判断为传输中断，后者为缺失依赖；需独立验证。  
**修复方法** → 稳定网络后重试大包；按约束补齐 `typeguard`。  
**验证方式** → 包校验成功且 `pip check` 不再报告对应项。  
**迁移经验** → 根据失败阶段分类比根据错误颜色分类可靠。

## 二、命令与配置解析类

### CLI 入口变化

**现象** → `python -m lerobot.record` 找不到模块。  
**第一判断** → 包没有安装。  
**日志证据** → LeRobot 可导入，但模块路径不存在；系统提供 `lerobot-record`。  
**排查步骤** → `which lerobot-record`、`lerobot-record --help`。  
**真正原因** → 当前版本使用 console entry point。  
**修复方法** → 改用 `lerobot-record`。  
**验证方式** → 本地帮助正常显示。  
**迁移经验** → 参数和入口以本地版本为准。

### YAML/字典与引号

**现象** → 相机参数在连接硬件前就解析失败。  
**第一判断** → 相机索引错误。  
**日志证据** → parser traceback 指向字典字符串，曾出现字段间缺逗号。  
**排查步骤** → 检查英文/中文引号、括号、逗号和 shell 外层引号。  
**真正原因** → 配置语法错误。  
**修复方法** → 使用格式正确的英文引号字典，并先用最小参数验证。  
**验证方式** → 解析通过后才进入相机连接日志。  
**迁移经验** → 解析层错误不应通过换硬件解决。

### 参数名随版本变化

**现象** → 网上示例中的 `resize_shape`、`crop_ratio` 或其他参数不被识别。  
**第一判断** → 拼写错误。  
**日志证据** → 当前 LeRobot 版本帮助仅列出 `crop_shape`。  
**排查步骤** → 对每个关键命令运行 `--help`，保留版本/commit。  
**真正原因** → 教程与本地 API 版本不同。  
**修复方法** → 使用本地支持的参数，并理解语义而不是寻找同名替代。  
**验证方式** → 配置解析和实际输入可视化都符合预期。  
**迁移经验** → 参数“能通过”仍不代表含义一致。

## 三、数据采集类

### 空 episode 与方向键事件

**现象** → 第三轮 Reset 时按键退出，设备断开后 `save_episode` 失败。  
**第一判断** → 相机断开造成保存失败。  
**日志证据** → Stop 先于 disconnect，保存空 episode 最后报错。  
**排查步骤** → 按时间排序 `Episode → Reset → key event → Stop → disconnect → save`。  
**真正原因** → 提前退出导致当前 episode 没有有效内容。  
**修复方法** → 在状态边界避免误触；保存前验证帧数，空 episode 直接丢弃。  
**验证方式** → 元数据、视频和 episode 计数一致。  
**迁移经验** → 清理日志不一定是根因。

### Hugging Face 401

**现象** → Hub 操作返回 401。  
**第一判断** → repo_id 或本地数据损坏。  
**日志证据** → HTTP 状态指向认证或权限。  
**排查步骤** → 检查当前身份、仓库所有者、可见性；不在日志和命令中粘贴 Token。  
**真正原因** → 未认证或无权限。  
**修复方法** → 本机安全登录，或将本地保存与上传解耦。  
**验证方式** → 最小只读请求成功后再上传。  
**迁移经验** → 本地成功和远端成功必须分别确认。

## 四、GPU 与训练类

### CUDA OOM、batch size 与碎片

**现象** → 15.47 GiB GPU 只余约 710 MiB，训练再申请约 830 MiB 失败。  
**第一判断** → 16GB 应该够，可能是程序 bug。  
**日志证据** → 进程已占约 13.47 GiB，峰值申请超过当时空闲空间。  
**排查步骤** → `nvidia-smi`、其他进程、batch size、双摄像头分辨率、allocated/reserved。  
**真正原因** → 当前负载超过可用显存，碎片可能进一步影响连续分配。  
**修复方法** → 降低 batch size；设置 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`。  
**验证方式** → 跨过原失败 step 并持续训练，记录峰值显存。  
**迁移经验** → allocator 选项不能替代降低实际负载。

### AMP、图像与双摄像头

**现象** → 训练/推理显存和耗时较高。  
**第一判断** → 只关注模型大小。  
**日志证据** → 双路 1280×720 图像及其增强/特征会增加输入和中间激活。  
**排查步骤** → 分别记录单/双相机、不同 batch 和 AMP 下的峰值与耗时。  
**真正原因** → 需要实验拆分，不能在当前记录中量化各项贡献。  
**修复方法** → 在模型支持时评估 AMP；合理预处理图像；保持训练部署一致。  
**验证方式** → 除资源下降外，还检查数值稳定和真机动作质量。  
**迁移经验** → 性能优化必须同时监控正确性。

### checkpoint 与恢复训练

**现象** → `last` 可以加载，但不确定是否是最好真机策略；恢复时也可能选错配置。  
**第一判断** → 最后一步自然最好。  
**日志证据** → loss 与真机成功并非单调对应，后期也可能过拟合或行为退化。  
**排查步骤** → 保存 checkpoint 对应 step、配置、数据版本和预处理。  
**修复方法** → 测试多个 checkpoint；恢复训练时从完整训练状态恢复，而不只加载权重。  
**验证方式** → 同条件重复真机评价。  
**迁移经验** → checkpoint 是实验快照，不只是一个文件名。

## 五、真机通信类

### `There is no status packet` 与 5 号舵机上扭矩失败

**现象** → Feetech 返回 `There is no status packet`，5 号舵机上扭矩失败。  
**第一判断** → 立即重新运行舵机配置命令。  
**日志证据** → 这条信息只说明控制器没有收到预期响应，不能单独区分断电、线材、端口占用、ID、波特率或舵机故障。  
**排查步骤** → 停止其他占用串口的进程；确认电源与共地；检查线材和串接位置；读取已知 ID；核对波特率；交换位置判断故障是否随舵机/线材移动。  
**真正原因** → 当前记录没有足够证据锁定唯一原因，应保留为通信链路待验证问题。  
**修复方法** → 先修复物理链路或占用问题，再做只读扫描；只有确认配置错误后才写入 ID/波特率。  
**验证方式** → 多次稳定读到状态包，再低风险上扭矩；不能以“命令不报错一次”作为唯一依据。  
**迁移经验** → 总线配置写操作具有风险，通信失败时先做可逆、只读检查。
